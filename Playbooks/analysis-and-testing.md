# 분석하고 테스트하기

기존 코드의 호출 흐름을 먼저 이해하고 의미 있는 노드를 테스트 대상으로 연결한다.

## 사용하는 경우

코드 변경 전에 영향과 테스트 경계를 찾아야 할 때 사용한다.

- Controller, Service 또는 배치 진입점의 호출 관계를 파악한다.
- 외부 의존과 데이터 저장 지점을 찾는다.
- 분기, 검증과 데이터 가공이 있는 테스트 대상을 고른다.
- 호출 분석 결과로 단위 테스트를 작성한다.
- 구조 전환 전에 현재 흐름을 기록한다.

## 1. 진입점 정하기

분석 단위는 실제 업무 흐름을 시작하는 지점으로 잡는다.

- Controller API
- Service 공개 메서드
- 배치 Job 또는 Step
- 메시지 Consumer
- 이벤트 Handler

대형 파일은 메서드나 API 경로로 범위를 좁힌다.

## 2. 호출 흐름 만들기

업무 판단과 외부 경계를 중심으로 호출을 펼친다.

```text
주문 요청
├─ 주문 검증
├─ 결제 승인
│  ├─ 한도 확인
│  └─ 외부 PG 호출
├─ 주문 저장
└─ 알림 발행
```

다음 항목을 표시한다.

- 분기와 검증
- 상태 변경
- Repository와 Mapper
- 외부 API와 메시지
- 트랜잭션 경계
- 테스트 가치가 있는 협력 메서드

getter, 로깅과 단순 DTO 필드 설정은 기본 흐름에서 제외한다.

## 3. 테스트 대상 판정

행동과 결과가 있는 노드를 선택한다.

테스트 가치가 높은 대상:

- 조건에 따라 결과가 달라진다.
- 입력을 검증하거나 예외를 발생시킨다.
- 데이터를 계산하거나 변환한다.
- 상태를 변경한다.
- 외부 시스템과 상호작용한다.

단순 위임은 상위 테스트에서 이미 검증되는지 확인한다.

## 4. 실제 소스와 대조하기

분석 문서만으로 테스트를 만들지 않는다.

- 현재 메서드 시그니처
- 실제 분기와 예외
- 외부 의존과 Mock 경계
- 기존 fixture와 테스트 스타일
- 저장 결과와 반환 계약

## 5. 테스트 작성과 실행

프로젝트의 기존 테스트 구조를 따른다.

- 정상과 주요 예외 시나리오
- 분기별 입력과 결과
- 외부 의존의 호출과 미호출
- 상태 변경과 저장 결과
- 실행 명령과 결과

## 완료 기준

분석 결과가 테스트와 후속 변경의 근거가 되어야 한다.

- 진입점과 분석 범위가 분명하다.
- 업무 분기와 외부 경계를 확인할 수 있다.
- 테스트 대상의 선택 이유가 있다.
- 실제 소스와 분석 문서를 대조했다.
- 실행 결과와 남은 미검증 범위를 구분했다.
