# 로드형의 Spring Security

Security 문서는 인증, 인가, 필터 체인과 토큰 운영이 중심인 작업에 사용한다.

## 사용하는 경우

요청이 어떤 근거로 허용되거나 거절되는지 정한다.

- `SecurityFilterChain`과 인증 흐름을 구성한다.
- URL과 메서드 권한을 설계한다.
- 401과 403 처리 기준을 맞춘다.
- JWT, 세션, OAuth2 인증을 적용한다.
- CORS, CSRF와 보안 헤더를 점검한다.
- Spring Security 버전 변경에 맞춰 설정을 전환한다.

## 필요한 입력

보안 설정과 업무 권한을 함께 전달한다.

- Spring Boot와 Spring Security 버전
- 현재 Security 설정과 인증 필터
- 사용자, 역할과 권한 모델
- 보호할 URL과 공개할 URL
- 세션 또는 토큰 정책
- 현재 401·403 증상과 로그

## 진행 기준

인증과 인가의 실패 지점을 분리한다.

1. 현재 필터 체인과 인증 객체 생성을 확인한다.
2. 공개 경로와 인증 필요 경로를 구분한다.
3. 역할과 권한 판정 위치를 정한다.
4. 인증 실패와 접근 거부 응답을 나눈다.
5. CORS, CSRF, 헤더와 토큰 운영 기준을 확인한다.
6. 성공, 미인증, 권한 부족 흐름을 테스트한다.

## 결과

보안 계약과 구현 위치를 함께 정리한다.

- 필터 체인과 인증 흐름
- URL·메서드 권한 규칙
- 401·403 응답 처리
- 토큰 발급, 만료, 갱신과 폐기 기준
- CORS, CSRF와 보안 헤더 설정
- 보안 테스트와 남은 운영 위험

## 요청 예시

```text
로드형, 관리자 API에 역할 기반 권한을 추가해줘.
Spring Boot와 Security 버전을 먼저 확인하고
미인증은 401, 권한 부족은 403으로 기존 오류 형식에 맞춰줘.
```

```text
로드형, JWT 갱신 흐름을 검토해줘.
Access Token과 Refresh Token의 만료, 재사용 차단과 로그아웃 기준까지 필요해.
```

## 확인 기준

보안 설정은 허용 경로와 실패 응답까지 검증한다.

- 현재 버전에 맞는 설정 방식을 사용한다.
- 공개 경로와 보호 경로가 목록으로 확인된다.
- 인증과 인가의 책임이 분리되어 있다.
- 401과 403 응답을 각각 검증했다.
- 토큰이나 세션의 운영 수명주기가 정의되어 있다.
- 루신과 권한별 회귀 범위를 확인한다.
