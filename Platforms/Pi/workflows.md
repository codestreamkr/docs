# Pi 작업 흐름

여러 결과가 필요한 작업에서는 앞 단계의 확정된 결과를 다음 Skill의 입력으로 연결해요.

문제 유형별 흐름과 단계별 판단 기준은 [Playbook](../../Playbooks/README.md)에서 관리해요.  
이 문서는 Pi에서의 호출과 연결 방법만 다뤄요.

## 호출과 연결

Skill 이름 앞에 `/skill:`을 붙이고, 앞 단계가 만든 결과를 다음 호출에서 지정해요.

```text
/skill:ct-plan-work 주문 취소의 중복 요청 방지 기능 구현 계획을 작성해줘
        ↓
/skill:ct-code-spring 확정된 계획을 기준으로 구현하고 관련 테스트를 실행해줘
        ↓
/skill:ct-qa-flow 주문 취소의 정상·중복·외부 실패 흐름을 검증해줘
```

다음 단계에 넘길 항목은 [Playbook 공통 기준](../../Playbooks/README.md#공통-기준)을 따르고, 대화만으로 대상을 구분하기 어려우면 결과 파일 경로를 함께 지정해요.

## 구현한 변경 검토하기

Pi에는 변경 검토 명령이 없어요.  
`pi review`와 `/review`는 없어요.

1. 변경 범위를 확인해요.

```bash
git diff
git status --short
```

2. diff를 넘겨 읽기 전용으로 검토해요.

```bash
git diff | pi --print "이 변경에서 동작 문제, 빠진 테스트, 요청 밖 변경만 짚어줘. 파일은 수정하지 마."
```

이미 연 세션이면 같은 기준으로 요청해요.

```text
현재 diff에서 동작 문제, 빠진 테스트, 요청 밖 변경만 짚어줘.
파일은 수정하지 마.
```

`--tools read,grep,find,ls`는 `bash`가 없어 diff를 조회하지 못해요.

3. 지적 사항의 근거를 확인하고, 수정과 재검증은 별도 요청으로 이어가요.

Spring 관례까지 보려면 `/skill:ct-code-spring`으로 읽기 전용 검토를 요청해요.

- 검토 응답만으로 수정이나 테스트까지 완료된 것으로 보지 않아요.

## 긴 작업의 맥락 관리

단계가 이어지면 현재 세션에 남은 맥락을 확인해요.

- `/session`: 현재 세션의 메시지 수, 토큰과 비용 확인
- `/compact`: 확정된 결과만 남기고 대화 요약
- `/new`: 앞 단계와 무관한 새 작업 시작

컨텍스트가 넘치면 Pi가 자동으로 요약해요.  
요약 기준을 바꾸려면 Settings의 `compaction.enabled`와 `compaction.keepRecentTokens`를 조정해요.

단계 사이에 맥락을 정리한 경우 다음 Skill 호출에 필요한 결과 문서와 경로를 다시 지정해요.

## 갈라서 비교하기

Pi는 세션을 트리로 다뤄요.  
앞 단계를 버리지 않고 다른 방향을 시도할 수 있어요.

| 상황 | 방법 |
| --- | --- |
| 앞 단계의 특정 지점으로 되돌아가 이어가요 | `/tree` |
| 이전 요청을 기준으로 다른 방향을 시작해요 | `/fork` |
| 현재 지점을 그대로 복제해 둘을 비교해요 | `/clone` |

`/tree`로 가지를 옮기면 옮기기 전 맥락은 요약으로 남아요.  
비교가 끝나면 채택한 결과의 문서 경로를 다음 Skill 호출에 지정해요.

## 반복 검증 자동화

같은 확인을 반복할 때는 대화형 대신 출력 모드로 실행해요.

```bash
# 결과 텍스트만 받기
pi -p "변경된 파일의 테스트만 실행하고 실패만 알려줘"

# 진행 상황을 구조화해 받기
pi --mode json "빌드하고 실패 원인을 정리해줘"
```

변경 검토는 [구현한 변경 검토하기](#구현한-변경-검토하기)를 봐요.

판단이 필요한 단계는 자동화하지 않아요.
