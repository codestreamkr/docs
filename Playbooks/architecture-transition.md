# 구조 전환하기

구조 전환은 현재 흐름, 목표 책임과 단계별 적용 순서를 함께 정한다.

## 사용하는 경우

기존 기능을 유지하면서 구조나 외부 의존을 바꿀 때 사용한다.

- 레거시 Service나 Client를 신규 구조로 교체한다.
- 기존 PG, 인증 또는 메시징 벤더를 전환한다.
- API 버전을 단계적으로 변경한다.
- 일정 기간 기존 구조와 신규 구조를 함께 운영한다.
- 데이터와 상태의 마이그레이션이 필요하다.

## 1. 현재 구조 확인

실제 진입점부터 저장과 외부 호출까지 기록한다.

- 호출 시작점
- 주요 Service와 데이터 접근
- 외부 API와 메시지
- 상태 저장과 변경
- 실패, 재시도와 운영 재처리
- 사용자와 다른 시스템에 노출된 계약

코드 호출 분석은 [분석하고 테스트하기](./analysis-and-testing.md)를 사용한다.

## 2. 목표 구조 결정

새 구조의 책임과 유지할 계약을 정한다.

- 신규 진입점과 서비스 책임
- 공통 계약과 구현체 경계
- 데이터와 상태 소유권
- 동기·비동기 처리 기준
- 타임아웃, 재시도와 멱등성
- 관측과 운영 도구

외부 연동은 [호페형](../Masters/hoppe/external-integration.md)과 먼저 설계한다.

## 3. 현재·목표 매핑

기존 구성요소가 어디로 이동하는지 표시한다.

| 현재 | 목표 | 처리 방식 |
| --- | --- | --- |
| 기존 API | 호환 API 또는 신규 버전 | 유지·변경·폐기 중 선택 |
| 레거시 Service | 신규 Service | 책임 이동 순서 정의 |
| 벤더 전용 상태 | 내부 공통 상태 | 변환 규칙 정의 |
| 운영 재처리 | 공통 운영 도구 | 이관과 권한 기준 정의 |

## 4. 단계별 적용

각 단계가 독립적으로 검증되고 롤백될 수 있게 나눈다.

1. 공통 계약과 관측 기준을 준비한다.
2. 신규 구조를 기존 흐름 옆에 추가한다.
3. 제한된 대상부터 라우팅한다.
4. 결과와 상태를 비교한다.
5. 적용 대상을 점진적으로 늘린다.
6. 기존 구조를 제거하고 운영 문서를 갱신한다.

## 5. 검증과 롤백

전환 전후에 같은 결과를 확인한다.

- 계약 호환성
- 상태와 데이터 정합성
- 중복 요청과 재시도
- 성능과 오류율
- 운영 조회와 재처리
- 롤백 조건과 복구 절차

루신과 단계별 회귀 범위를 정한다.

## 완료 기준

전환 계획은 구현과 운영이 함께 사용할 수 있어야 한다.

- 현재와 목표 호출 흐름이 있다.
- 구성요소와 메서드의 이동 관계를 확인할 수 있다.
- 단계별 적용 범위와 성공 기준이 있다.
- 병행 운영과 롤백 조건이 있다.
- 기존 구조 제거 조건과 문서 갱신 대상이 있다.
