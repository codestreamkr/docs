## 잡스형을 찾을 때

무엇을 왜 만들어야 하는지 먼저 정해야 하는 일을 맡긴다.

- 아이디어를 기능으로 구체화한다.
- 사용자 문제와 목표 상태를 정의한다.
- MVP와 후속 범위를 나눈다.
- 사용자 흐름과 화면 구조를 만든다.
- 정책, 예외, 운영 기준을 정리한다.
- PRD, 기능 정의서, 화면 설계서를 만든다.

## 먼저 알려줄 내용

처음부터 완성된 요구사항은 필요하지 않다.

- 기능을 사용할 사람
- 현재 겪는 문제
- 기능이 완성된 뒤 원하는 상태
- 일정, 기술, 운영상의 제약
- 이번에 결정해야 하는 범위
- 필요한 최종 문서

## 함께 진행하는 방식

잡스형은 화면보다 문제와 흐름을 먼저 정한다.

1. 사용자와 현재 문제를 정의한다.
2. 목표와 성공 기준을 정한다.
3. 이번 범위와 후속 범위를 나눈다.
4. 핵심 사용자 흐름과 상태를 만든다.
5. 화면, 정책, 예외와 운영 동작을 연결한다.
6. 개발과 디자인이 사용할 문서로 정리한다.

## 받을 수 있는 결과

요청 목적에 맞는 문서를 선택한다.

| 결과 | 내용 |
| --- | --- |
| 기획 방향 | 문제, 사용자, 목표, 범위 |
| 기능 정의서 | 정상·예외 동작과 완료 조건 |
| 사용자 흐름 | 진입, 분기, 완료, 이탈 |
| 화면 설계서 | 화면 목적, 상태, 요소, 인터랙션 |
| PRD | 배경, 요구사항, 범위, 성공 기준 |
| 열린 이슈 | 추가 합의가 필요한 정책과 제약 |

## 이렇게 시작한다

```text
잡스형, 회의록에서 담당자별 할 일을 뽑아주는 기능을 만들고 싶어.
회의가 끝난 뒤 해야 할 일이 누락되는 문제가 있어.
첫 번째 버전의 사용자 흐름과 기능 범위부터 정리해줘.
```

```text
PD, 운영팀이 주문 상태와 취소 요청을 한 화면에서 볼 수 있는
대시보드를 기획해줘. 역할별 권한과 주요 운영 액션도 포함해줘.
```

## 완료 기준

기획 결과는 구현 판단에 바로 사용할 수 있어야 한다.

- 사용자와 해결할 문제가 분명하다.
- 이번 범위와 후속 범위가 구분되어 있다.
- 정상, 빈 상태, 오류, 권한 차이를 확인할 수 있다.
- 사용자 흐름과 운영 흐름이 연결되어 있다.
- 구현 완료 여부를 판단할 기준이 있다.
