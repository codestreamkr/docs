# 계획하고 구현하기

개선 작업은 필요한 판단 단계만 거쳐 실제 코드 변경으로 연결한다.

## 작업 크기 판단

범위와 미결정 사항을 기준으로 단계를 고른다.

| 현재 상황 | 진행 방식 |
| --- | --- |
| 무엇부터 개선할지 모름 | 개선 과제와 우선순위부터 정한다 |
| 정책, 상태, 권한과 운영 영향이 큼 | 설계 결정을 먼저 남긴다 |
| 구현 계약이 분명함 | 바로 구현한다 |
| 기존 문서에 결정이 완료됨 | 문서를 구현 입력으로 사용한다 |

## 1. 개선 우선순위 정하기

코드와 설정을 근거로 개선 과제를 나눈다.

- 현재 문제와 영향
- 변경 대상과 범위
- 우선순위와 선행 조건
- 이번 단계와 후속 단계
- 바로 구현 가능한지 여부

이 단계에서는 운영 코드를 변경하지 않는다.

## 2. 설계 방향 결정하기

결과를 바꾸는 선택지만 검토한다.

- 참여해야 할 Master
- 대안별 장점, 위험과 운영 영향
- 의견이 충돌하는 지점
- 채택안, 제외안과 선택 이유
- 성공 기준과 재검토 조건

단일 버그나 작은 표시 변경은 이 단계를 생략한다.

## 3. 구현 범위 확정하기

계획과 설계 결과를 실제 변경 단위로 바꾼다.

- 바로 구현할 범위
- 확인된 가정으로 구현할 범위
- 정책 결정이 필요한 보류 범위
- 유지할 API, 데이터와 운영 계약
- 검증과 테스트 범위

## 4. 구현하고 검증하기

프로젝트의 기존 구조를 따라 변경한다.

- 진입점과 핵심 처리 흐름 확인
- 데이터 계약과 저장 경계 반영
- 연관 호출 경로의 전파 누락 확인
- 빌드와 정적 검증
- 요청된 테스트 작성과 실행
- 변경 범위와 남은 위험 정리

## 대표 흐름

### 범위가 큰 개선

1. 개선 항목과 우선순위를 정한다.
2. 필요한 항목만 설계 검토를 거친다.
3. 채택안과 성공 기준으로 구현한다.
4. 관련 회귀를 검증한다.

### 범위가 작은 기능

정책과 데이터 계약이 명확하면 구현과 검증만 수행한다.

```text
게시판 목록 API에 작성자 이름 필드를 추가해줘.
기존 응답과 null 처리 기준을 유지하고 관련 검증까지 실행해줘.
```

## 완료 기준

문서와 코드의 책임이 섞이지 않아야 한다.

- 우선순위 판단과 코드 변경을 구분했다.
- 결과를 바꾸는 선택에는 결정 근거가 있다.
- 확정된 범위만 운영 코드에 반영했다.
- 구현 결과와 테스트 결과를 구분했다.
- 후속 항목과 미확정 정책을 남겼다.
