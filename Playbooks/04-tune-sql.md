# 느린 SQL 개선하기

같은 조건에서 병목을 측정하고, 변경 뒤 성능과 결과 동등성을 확인해요.

## 흐름

```text
ct-data-query     재현 조건, 실행 계획과 변경 전 수치 확인
      ↓
ct-plan-work      여러 개선안의 적용 순서와 위험 확정  ← 단계별 변경이 필요할 때
      ↓
ct-code-spring    Mapper와 관련 코드 수정             ← 코드 변경이 필요할 때
      ↓
ct-qa-flow        같은 조건의 성능·결과·회귀 검증
```

## 다음 단계로 넘어갈 기준

- 추정만으로 인덱스를 추가하지 않아요. 실행 계획과 변경 전 수치를 확보해요.
- 인덱스의 쓰기 비용, 쿼리 재작성의 결과 동등성, 스키마 변경의 배포·롤백 순서를 변경안에 맞춰 검토해요.
- 쿼리나 인덱스만 변경하면 코드 구현 단계는 생략해요. 여러 변경을 단계적으로 적용해야 할 때만 별도 계획을 세워요.
- 같은 조건의 변경 전후 수치와 결과를 비교하고 다른 조회의 회귀를 확인해요.
- 개선되지 않은 병목과 검증하지 못한 범위를 남겨요.

## 다른 흐름을 쓸 때

병목이 쿼리가 아니라 호출 구조에 있으면 먼저 해당 코드의 호출 흐름을 조사해요.
