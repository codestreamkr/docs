# 기능 구현하고 검증하기

확정된 계획을 현재 프로젝트 관례에 맞춰 반영하고 실패 경로까지 검증한다.

## 흐름

```text
ct-plan impl     변경 대상, 영향, 구현 순서와 검증 기준       ← 계획이 이미 있으면 생략
      ↓
ct-spring        확인한 환경, 변경 내용, 영향 범위와 검증 결과
      ↓
ct-qa-lucin      검증 범위, 위험별 시나리오와 실행 결과
```

## 단계별로 확정할 것

### ct-plan impl

계획 문서가 이미 있으면 이 단계를 생략하고 해당 문서를 구현 입력으로 사용한다.

- 변경할 파일과 계층
- 유지할 API와 데이터 계약
- 구현 순서
- 검증 기준

### ct-spring

- 현재 프로젝트의 버전과 구성을 먼저 확인했는지
- 기존 계층 구조와 응답 형식을 유지했는지
- 변경한 파일과 영향 범위
- 실행한 빌드와 테스트, 그 결과

계획에 없던 변경이 필요해지면 임의로 확장하지 않고 범위를 다시 확정한다.

### ct-qa-lucin

- 정상 흐름뿐 아니라 권한, 중복 요청, 실패 복구
- 위험이 높은 순서로 정한 시나리오
- 실행한 검증과 그 결과
- 재현 방법
- 실행하지 못한 범위

## 다음 단계로 넘길 것

- 변경 파일과 실제 반영 내용
- 계획 대비 달라진 부분과 그 이유
- 검증 결과와 미검증 범위
- 남은 위험과 후속 작업

## 이 Playbook을 벗어나는 경우

- 무엇을 만들지가 아직 흐릿하면 [01](./01-define-scope.md)로 돌아간다.
- 변경 대상 코드의 호출 관계를 모르면 [03](./03-understand-code.md)을 먼저 진행한다.
- 배포 직전 전체 위험을 훑어야 하면 [08](./08-verify-before-release.md)을 사용한다.
