# 어려운 문제 풀기

어려운 문제는 바로 해결안을 고르기보다 현재 증상, 필요한 판단과 담당 Master를 먼저 구분한다.

## 1. 문제를 한 문장으로 적기

관찰한 사실과 원하는 상태를 함께 적는다.

```text
주문 취소가 간헐적으로 실패하고 운영자가 수동으로 상태를 맞추고 있다.
중복 요청과 외부 PG 지연에도 같은 결과가 되도록 만들고 싶다.
```

## 2. 현재 단서 모으기

판단에 사용할 수 있는 근거를 먼저 모은다.

- 재현 절차와 오류 메시지
- 관련 코드, 로그와 문서
- 최근 변경사항
- 영향을 받는 사용자와 데이터
- 유지해야 하는 계약
- 시간, 운영과 보안 제약

## 3. Master 선택

문제의 중심 판단을 맡을 Master를 고른다.

| 중심 문제 | 먼저 찾을 Master |
| --- | --- |
| 사용자 문제, 기능 범위와 정책이 불명확함 | [잡스형](../Masters/jobs/product-planning.md) |
| SQL, 실행 계획과 DB 부하가 중심임 | [대부님](../Masters/godfather/query-tuning.md) |
| Spring 코드, 계층과 트랜잭션이 중심임 | [로드형](../Masters/rod/README.md) |
| 외부 API, 웹훅과 상태 경계가 중심임 | [호페형](../Masters/hoppe/external-integration.md) |
| 재현, 테스트 범위와 품질 위험이 중심임 | [루신](../Masters/lucin/quality-assurance.md) |

중심 문제가 바뀌면 다음 Master에게 현재까지의 결과를 전달한다.

## 4. 해결 단위 정하기

현재 단계에서 필요한 결과만 요청한다.

- 원인 분석
- 정책과 범위 결정
- 목표 구조 설계
- 코드 구현
- 결함 재현과 테스트
- 운영 전환 계획

## 5. 결과 연결

앞 단계 결과를 다음 작업의 입력으로 사용한다.

```text
호페형이 정리한 현재 상태와 멱등성 기준을 바탕으로
로드형이 Spring 구현 범위를 정하고 반영한다.
그 결과를 루신이 중복 요청과 타임아웃 시나리오로 검증한다.
```

## 완료 기준

어려운 문제는 모든 불확실성을 없애는 대신 다음 행동을 명확히 한다.

- 관찰한 사실과 추정이 구분되어 있다.
- 중심 문제와 담당 Master가 정해졌다.
- 현재 단계의 결과와 완료 조건이 있다.
- 다음 단계에 전달할 입력이 남아 있다.
- 미확정 정책과 기술 위험이 구분되어 있다.
