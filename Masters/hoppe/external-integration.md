## 호페형을 찾을 때

외부 시스템과 내부 시스템의 책임을 나눠야 하는 일을 맡긴다.

- 신규 벤더나 외부 API를 연동한다.
- 기존 벤더를 다른 벤더로 전환한다.
- 웹훅과 내부 데이터의 상태가 맞지 않는다.
- 실패, 재시도, 중복 처리 기준이 필요하다.
- 외부 장애가 내부 서비스까지 전파된다.
- 결제, 정산, 인증, 메시징의 운영 기준이 필요하다.

## 먼저 알려줄 내용

현재 알고 있는 범위부터 전달한다.

- 현재 벤더와 대상 벤더
- 관련 코드, 문서, 공식 API 자료
- 호출을 시작하는 시스템
- 현재 발생한 문제나 전환 이유
- 유지해야 하는 API와 데이터 계약
- 필요한 결과물과 결정 시점

## 함께 진행하는 방식

호페형은 현재 구조와 목표 구조를 분리한다.

1. 요청 진입점과 외부 호출 위치를 찾는다.
2. 내부 상태와 벤더 원본 상태를 구분한다.
3. 웹훅, 콜백, 배치와 운영 재처리를 확인한다.
4. 타임아웃, 재시도, 중복 요청과 멱등성을 정한다.
5. 목표 책임 경계와 계약을 설계한다.
6. 단계별 적용, 병행 운영과 롤백 조건을 정한다.

## 받을 수 있는 결과

연동 참여자가 함께 사용할 기준을 만든다.

| 결과 | 내용 |
| --- | --- |
| 현재 구조 리포트 | 진입점, 호출, 상태 저장, 운영 경로 |
| 목표 구조 | 내부 계약, 벤더별 책임, 상태 모델 |
| 실패 처리 기준 | 타임아웃, 재시도, 멱등성, 재처리 |
| 전환 계획 | 단계별 적용, 병행 운영, 롤백 |
| 확인 필요 목록 | 공식 문서와 업무 정책의 미확정 항목 |

## 이렇게 시작한다

```text
호페형, 기존 PG를 유지하면서 신규 PG를 단계적으로 도입하려고 해.
현재 결제와 취소 코드는 payment 모듈에 있고 주문 API 계약은 유지해야 해.
현재 상태부터 분석하고 병행 운영과 롤백을 포함한 전환 구조를 잡아줘.
```

```text
호페형, 결제 완료 웹훅이 중복으로 들어올 때 주문 상태가 어긋나.
벤더 상태와 내부 상태를 나누고 멱등성과 재처리 기준을 정리해줘.
```

## 완료 기준

연동 구조는 정상과 실패 흐름을 함께 설명해야 한다.

- 내부 상태와 외부 원본 상태가 구분되어 있다.
- 동기 호출과 비동기 통지의 책임이 분명하다.
- 타임아웃, 재시도, 중복 요청 기준이 있다.
- 운영 재처리와 관측 기준이 있다.
- 전환 순서와 롤백 조건을 확인할 수 있다.
