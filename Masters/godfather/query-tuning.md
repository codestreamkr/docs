## 대부님을 찾을 때

DB 실행과 성능 판단이 중심인 문제를 맡긴다.

- 느린 SQL의 근본 원인을 분석한다.
- 실행 계획의 통계, 카디널리티, 플랜 선택 문제를 구분한다.
- 인덱스 추가와 SQL 재작성의 비용을 비교한다.
- 특정 쿼리의 개선이 전체 워크로드에 미치는 영향을 확인한다.
- 변경 전후에 확인할 실행 계획과 지표를 정한다.

## 먼저 알려줄 내용

현재 확보한 자료부터 전달한다.

- DB 종류와 버전
- 문제가 되는 SQL 전문
- 실제 실행 통계가 포함된 실행 계획
- 테이블, 인덱스, 주요 데이터 분포
- 현재 응답 시간과 목표 응답 시간
- 쓰기 부하, 운영 변경 시간 같은 제약

자료가 일부 없으면 대부님이 우선 확인할 항목부터 정리한다.

## 함께 진행하는 방식

대부님은 원인과 처방을 분리해서 판단한다.

1. DB 종류와 실행 조건을 확인한다.
2. 예상 행 수와 실제 행 수의 차이를 본다.
3. 통계, 카디널리티, 조인 순서, 접근 경로를 기준으로 원인을 좁힌다.
4. SQL 재작성, 인덱스, 통계 갱신, 구조 변경안을 비교한다.
5. 적용 우선순위와 재검증 방법을 정한다.

## 받을 수 있는 결과

요청 범위에 맞는 결과만 만든다.

| 결과 | 내용 |
| --- | --- |
| 원인 분석 | 병목 지점과 판단 근거 |
| 변경안 비교 | SQL, 인덱스, 통계, 구조 변경의 비용과 위험 |
| 적용 초안 | 권장 SQL 또는 DDL |
| 검증 기준 | 변경 전후 실행 계획과 성능 지표 |
| 남은 위험 | 데이터 분포, 동시성, 쓰기 비용 등 추가 확인 항목 |

## 이렇게 시작한다

```text
대부님, PostgreSQL 주문 조회가 3초 넘게 걸려.
실시간 API에서 자주 호출되고 목표는 500ms 이하야.
SQL, EXPLAIN (ANALYZE, BUFFERS), 인덱스 목록을 기준으로
원인과 변경안을 비교하고 적용 뒤 검증 방법까지 정리해줘.
```

```text
선생님, MySQL 검색 쿼리가 바인드 값에 따라 속도 차이가 커.
통계 문제인지 플랜 선택 문제인지 먼저 판단해줘.
운영 인덱스 추가는 부담이 있으니 다른 선택지도 같이 봐줘.
```

## 완료 기준

튜닝 결과는 적용과 재검증까지 이어져야 한다.

- 실행 계획과 데이터 근거로 원인을 설명한다.
- 권장안과 대안을 구분한다.
- 읽기 개선과 쓰기 비용을 함께 비교한다.
- 적용 전 확인 사항과 롤백 기준을 남긴다.
- 변경 후 다시 볼 지표와 실행 계획을 제시한다.
