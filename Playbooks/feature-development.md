# 새로운 기능 만들기

새 기능은 문제와 범위를 정하고, 프로젝트에 맞게 구현한 뒤 실제 위험을 검증한다.

## 기본 흐름

기획, 구현과 검증의 책임을 구분한다.

```text
잡스형과 기능 범위 결정
→ 필요한 경우 호페형·대부님과 전문 설계
→ 로드형과 구현
→ 루신과 검증
```

## 1. 잡스형과 범위 정하기

아이디어를 구현 가능한 기준으로 바꾼다.

필요한 결과:

- 해결할 사용자 문제
- 이번 범위와 후속 범위
- 사용자와 운영 흐름
- 주요 정책과 예외
- 구현 완료 조건

요청 예시:

```text
잡스형, 회의록에서 담당자별 할 일을 추출하는 기능을 만들고 싶어.
첫 번째 버전의 사용자 흐름, 기능 범위와 완료 조건을 정리해줘.
```

## 2. 필요한 전문 설계 추가

기능 성격에 맞는 Master만 추가한다.

- 외부 서비스 계약과 상태: 호페형
- 조회 성능과 인덱스: 대부님
- Spring API, 보안과 데이터 접근: 로드형

정책과 계약이 이미 분명하면 별도 설계 단계를 생략한다.

## 3. 로드형과 구현하기

확정된 기획과 설계를 프로젝트 구조에 반영한다.

필요한 결과:

- 변경할 API와 데이터 계약
- 계층별 구현 책임
- 운영 코드와 설정
- 빌드와 기본 검증 결과
- 남은 위험

요청 예시:

```text
로드형, 잡스형이 정리한 기능 문서를 기준으로 구현해줘.
기존 프로젝트 구조와 응답 형식을 유지하고 관련 테스트도 실행해줘.
```

## 4. 루신과 검증하기

기획의 완료 조건과 실제 구현을 대조한다.

필요한 결과:

- 위험별 테스트 범위
- 정상, 예외, 권한과 재진입 검증
- 자동화 테스트와 실행 결과
- 발견한 결함과 남은 위험

요청 예시:

```text
루신, 구현된 기능을 기획 문서와 대조해 검증해줘.
정상 흐름뿐 아니라 권한, 중복 요청과 실패 복구도 확인해줘.
```

## 완료 기준

기획, 코드와 검증 결과가 같은 범위를 가리켜야 한다.

- 사용자 문제와 구현 범위가 연결되어 있다.
- API와 데이터 계약이 확정되어 있다.
- 구현 결과가 완료 조건을 충족한다.
- 주요 예외와 권한 흐름을 검증했다.
- 자동화 범위와 운영 전 확인 사항을 구분했다.
