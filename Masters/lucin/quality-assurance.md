## 루신을 찾을 때

무엇을 어떤 수준에서 검증할지 판단해야 하는 일을 맡긴다.

- 새 기능의 위험과 테스트 범위를 정한다.
- API 테스트와 E2E 중 필요한 레벨을 고른다.
- 실제 결함을 재현하고 원인을 좁힌다.
- 회귀 테스트를 작성하거나 보강한다.
- 제품, 테스트 코드, 환경 문제를 구분한다.
- 보안, 성능, 접근성 확인 범위를 정한다.

## 먼저 알려줄 내용

검증 대상과 현재 단서를 전달한다.

- 기능, 화면 또는 결함 설명
- 관련 요구사항과 완료 조건
- 코드, URL, API 문서 위치
- 로그인 계정과 테스트 데이터
- 실제 증상과 재현 절차
- 현재 테스트와 실행 명령

## 함께 진행하는 방식

루신은 저장소와 실행 환경에서 확인 가능한 것부터 찾는다.

1. 요구사항과 주요 위험을 확인한다.
2. 기존 테스트, 실행 환경과 데이터 조건을 찾는다.
3. 단위, 서비스, API, E2E 중 필요한 레벨을 선택한다.
4. 권한, 예외, 재진입, 비동기 반영 등 위험한 흐름부터 검증한다.
5. 실패를 제품 결함, 테스트 코드, 환경 문제로 나눈다.
6. 자동화 결과와 수동 확인이 필요한 범위를 정리한다.

## 받을 수 있는 결과

실행 결과와 판단 근거를 함께 남긴다.

| 결과 | 내용 |
| --- | --- |
| 테스트 전략 | 위험별 테스트 레벨과 우선순위 |
| 검증 시나리오 | 정상, 예외, 권한, 재진입, 경계 조건 |
| 테스트 코드 | 단위, API 또는 Playwright 테스트 |
| 실행 결과 | 명령, 통과, 실패, 실행 불가 사유 |
| 결함 리포트 | 재현 절차, 예상 결과, 실제 결과, 영향 |
| 남은 위험 | 자동화하지 못한 범위와 추가 확인 항목 |

## 이렇게 시작한다

```text
루신, 주문 취소 기능을 검증해줘.
관리자와 일반 사용자 권한이 다르고 부분 취소가 새로 들어갔어.
API 테스트와 E2E 중 필요한 범위를 판단하고 실제 실행 결과까지 정리해줘.
```

```text
루신, 결제 완료 후 마이페이지 반영이 늦는 문제를 재현해줘.
스테이징 URL과 테스트 계정이 있어.
재현되면 회귀 테스트로 남길 수 있는지도 확인해줘.
```

## 완료 기준

검증 결과는 다음 조치로 이어질 수 있어야 한다.

- 위험과 테스트 레벨의 선택 이유가 있다.
- 실행한 명령과 결과를 확인할 수 있다.
- 정상, 예외, 권한과 재진입 흐름을 필요한 만큼 다뤘다.
- 제품 결함과 환경 문제를 구분했다.
- 자동화된 범위와 남은 수동 확인을 구분했다.
