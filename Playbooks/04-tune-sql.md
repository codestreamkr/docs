# 느린 SQL을 개선한다

측정 근거를 먼저 확보하고, 코드 변경이 필요한 경우에만 구현을 연결한다.

## 흐름

```text
ct-query-tuner   분석 조건, 병목 근거와 우선순위가 있는 개선안
      ↓
ct-plan impl     적용과 검증 순서                        ← 쿼리·인덱스 변경만이면 생략
      ↓
ct-spring        Mapper와 관련 코드 수정                  ← 코드 변경이 있을 때만
      ↓
ct-qa-lucin      결과 동등성과 회귀 범위 검증
```

## 단계별로 확정할 것

### ct-query-tuner

- 대상 쿼리와 재현 조건
- 실행 계획에서 확인한 병목 근거
- 개선안과 각각의 적용 비용
- 변경 전 수치

추정 원인이 아니라 실행 근거를 받는다. 근거 없이 인덱스부터 추가하지 않는다.

### ct-plan impl

개선안이 여러 개면 무엇을 먼저 적용할지와 각각의 위험을 확정한다.

- 인덱스 추가: 쓰기 비용과 저장 공간
- 쿼리 재작성: 결과 동등성
- 스키마 변경: 배포 순서와 되돌리기

쿼리나 인덱스 변경만으로 끝나면 이 단계와 다음 단계를 사용하지 않는다.

### ct-spring

확정된 개선안만 반영한다. 이 단계에서 새 개선안이 나오면 되돌아가 근거부터 확인한다.

### ct-qa-lucin

- 변경 전후 수치를 같은 조건에서 비교했는지
- 결과가 이전과 동일한지
- 같은 테이블을 사용하는 다른 조회의 회귀

## 다음 단계로 넘길 것

- 적용한 개선안과 제외한 대안
- 재현 조건과 변경 전후 수치
- 유지해야 할 결과 계약
- 남은 병목과 후속 과제
